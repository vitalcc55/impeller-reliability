# Политика и стратегия тестирования

## Область и результат

Этот файл — единственный источник правил написания тестов и выбора проверок для всего репозитория. Корневой `AGENTS.md` направляет сюда перед работой с тестовым контуром. Тесты остаются рядом со своими владельцами в `apps/desktop`, `packages` и `tools/python-worker`; переносить их в этот каталог не нужно.

Цель — обнаруживать существенные ошибки минимальным достаточным набором быстрых, понятных и независимых проверок. Количество тестов и процент coverage сами по себе не доказывают качество.

## Как писать и менять тесты

- Сначала назови наблюдаемый контракт, ошибку, которую тест должен обнаружить, и начальные условия. Проверяй результат через границу владельца; не закрепляй частные функции, ссылочную идентичность или CSS-структуру, если они не являются контрактом.
- Выбирай самый лёгкий уровень, который доказывает нужное поведение. Проверка логики не требует DOM, а DOM-взаимодействие — запуска Electron. Реальные процессы нужны для IPC, lifecycle и системных границ.
- Ожидаемые значения задавай независимо от проверяемой реализации. Не вычисляй эталон тем же production helper. Сохраняй значимые границы: ноль, `false`, `null`, лимиты, округление, stale revision и ошибки.
- Для исправления воспроизведи дефект и закрепи его существующим подходящим тестом либо минимальной regression-проверкой. Не добавляй тесты тестового контура, структуры helpers/fixtures, фиксированных ответов DEV-заглушек или декоративных деталей UI. Snapshot внешнего контракта и проверка provenance исходных байтов защищают продуктовый контракт и сохраняются.
- Перед новым сценарием проверь существующее покрытие. Удаляй эквивалентные проверки на одной границе; проверки разных границ допустимы, если каждая ловит свой отказ. Независимые оси параметров проверяй отдельно; их произведение нужно при существенном взаимодействии.
- Имена файлов, тестов, helpers и fixtures выражают ответственность, контракт или инвариант. Не используй номера этапов, задач и релизов. Сохраняй каноническую терминологию; имена утверждённых внешних контрактов и их версии не переименовывай ради этого правила.

## Где проверять

| Контур | Что он доказывает |
| --- | --- |
| TypeScript / Node | Runtime contracts, безопасные DTO, draft/reconciliation, queue/deadlines/drain. Настоящий child process — для JSONL и lifecycle. |
| React / DOM | Пользовательские действия, pending/dirty/stale answers, доступные состояния, клавиатуру и focus. DOM-окружение включается только файлам, которым оно нужно. |
| Python | Независимые инженерные эталоны, единицы и округление; ZIP/security/streaming; SQLite transactions, audit, immutable provenance, retry, reopen и corruption. |
| Electron E2E | Реальные Main → sandboxed Preload → worker → SQLite и существенные пользовательские развилки: import/save/reopen, dirty/close/crash/restart, история за первой страницей и границы открытия материалов. Не повторяй здесь полные матрицы низкоуровневых ошибок. |
| Packaged smoke | Настоящие WinUnpacked и установленный NSIS payload с bundled worker: fuses/CSP/integrity, import/calculations/materials/reopen, N→N+1 readback того же дела/профиля, repair/downgrade/uninstall/reinstall. Отсутствие TCP и orphan worker только в собственном process tree; ошибка обязательного наблюдения завершает smoke с отказом. Retry/Cancel дополнительно проверяются настоящим UI-проходом. |

Synthetic Browser preview проверяет renderer, но не расчёты, IPC или persistence и не заменяет Electron E2E и packaged smoke.

## Подготовка, изоляция и ресурсы

- Переиспользуй существующие fixtures и общую подготовку, когда это уменьшает реальные повторы. Общие данные не должны превращаться в общее изменяемое состояние или зависимость от порядка тестов. Последовательность допустима, когда её переходы и есть проверяемый пользовательский сценарий.
- Каждая независимая проверка начинает с нужного исходного состояния. В cache-invalidation сценарии заново подтверди verified cache перед его повреждением; для проверки reopen открой свежий repository. Простое объединение тестов не сохраняет эти условия автоматически.
- Создавай только нужные ресурсы: отказ до ZIP-разбора не требует полноценного архива; чистая логика не требует большого файла или GUI. Новые helpers и универсальные test harness добавляй только при подтверждённом повторении.
- Ограничивай параллелизм по конфигурации и ресурсам машины, сохраняй изоляцию. Освобождай свои процессы, соединения и временные файлы через гарантированную очистку, включая путь ошибки; чужие процессы не останавливай.
- Переиспользуй свежие артефакты текущего прогона, пока их входы не изменились; не повторяй их сборку. Порядок сборки и самостоятельная проверка prerequisites package-команд принадлежат [Windows Setup](../docs/packaging/WINDOWS_SETUP.md).
- Не маскируй failures через retry, увеличение timeout, `skip`, слабые assertions или обход auth/integrity. Действующие deadlines, нулевые retries и Python branch coverage gate 85% сохраняются. Параметры запуска принадлежат [Vitest](../vitest.config.ts), [Playwright](../playwright.config.ts) и [Python configuration](../tools/python-worker/pyproject.toml).
- Измеряй эффект на сопоставимых запусках. Различай wall-clock, сумму времени workers, CPU и peak RAM; не выдавай единичный снимок за пиковое потребление. Сырые логи и evidence храни в ignored `.tmp/.codex/evidence/`.

## Эталоны и fixtures

Golden fixture хранит источник и его revision/hash, canonical input, промежуточные и итоговые значения, единицы, округление, tolerance и reviewer. Демонстрационный пример не становится эталоном автоматически. Конкретная provenance и значения принадлежат самим [инженерным эталонам](../fixtures/golden/), например [эталону РБД](../fixtures/golden/rbd-reference-v1.json), а не отдельной памятке.

Synthetic builder создаёт согласованные данные только во временном каталоге и не считается golden. Frozen upstream packages сохраняют первичные байты и provenance; не обновляй эталоны и ожидаемые значения только ради зелёного теста.

## Как выбирать и запускать проверки

1. Во время изменений запускай только целевые проверки затронутого владельца. Для unit: `pnpm exec vitest run <file>` или `uv run --project tools/python-worker pytest <file> --no-cov`; для реального Electron — `pnpm exec playwright test <file> --grep <scenario>`. `--no-cov` допустим для узкого Python-запуска, полный gate всегда измеряет branch coverage.
2. Для существенного renderer-изменения запусти `pnpm dev:preview` и проверь через встроенный Browser `http://127.0.0.1:5173/?preview=ready` и `http://127.0.0.1:5173/?preview=unavailable`: роли, landmarks, status/alert, keyboard/focus, поддерживаемый desktop viewport и сохранность существующего defensive reflow в узком окне, затем консоль. Границы поддержки задаёт [DESIGN.md](../DESIGN.md); этот проход не расширяет их. Playwright не заменяет наблюдаемую Browser-проверку. Дизайн-процесс задаёт корневой `AGENTS.md`.
3. После review выполни необходимые gates по затронутой границе. Для изменений кода минимальный общий gate — `pnpm check`; renderer/Main/Preload дополнительно требуют Electron E2E, packaging boundary — self-test worker и оба packaged smoke. Изменение только Markdown проверяй чтением diff, ссылок и согласованности инструкций без запуска приложения и тестов.
4. Повторяй или расширяй проверки после исправления failures, новых изменений или при оставшемся конкретном риске. Полный gate уже включает свои составляющие: не запускай их дополнительно перед ним или после него без основания. После успешной достаточной проверки переходи к завершению задачи.

| Gate | Команды из корня репозитория |
| --- | --- |
| Static/unit TypeScript и Python | `pnpm check` |
| Только Python static/unit | `pnpm check:python` |
| Electron build/E2E | `pnpm build`; `pnpm test:e2e` |
| Worker artifact/self-test | `pnpm build:worker`; `pnpm smoke:worker` |
| WinUnpacked | `pnpm package:win-unpacked`; `pnpm smoke:win-unpacked` |
| NSIS Setup / installed lifecycle | `pnpm package:setup`; `pnpm smoke:setup` (требует отсутствующей установки/ярлыков; создаёт два настоящих тестовых выпуска, затем удаляет свою установку, сохраняя дело/профиль в evidence) |
| Полный локальный gate с установкой | `pnpm verify -- --IncludePackaging` |

Python static-проверки из `tools/python-worker`: `uv run ruff format --check src tests`, `uv run ruff check src tests`, `uv run mypy`, `uv run pyright`. Версии и параметры инструментов принадлежат конфигурации проекта.

Цель доступности принадлежит [требованиям](../docs/requirements/REQUIREMENTS.md). В Browser/Electron дополнительно пройди изменённый сценарий только клавиатурой, проверь порядок и возврат фокуса, status/alert, reduced motion и сохранность существующего defensive reflow в границах `DESIGN.md`. Автоматизация не подтверждает доступность целиком: перед production release реальных расчётных таблиц и графиков нужны ручные проверки NVDA, Narrator, Windows High Contrast и DPI/text scaling.

## Критерий завершения

Проверь, что нужный контракт доказан, начальные условия не ослаблены, дубли удалены без потери единственного доказательства, а подтверждённые findings закрыты. Сообщи, что именно проверено, какими командами и с каким результатом; непроверенное не называй подтверждённым. Не веди в политике перечень всех тестов, историю этапов или копию статуса текущей задачи.
